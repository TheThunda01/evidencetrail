# Assumptions and their consequences

EvidenceTrail has no biological model. Its assumptions concern extraction records, text comparison, and software operation. The table separates rules the software checks from conditions a review team must establish.

| Assumption or choice | Why it is used | How it is checked | Consequence if it fails |
| --- | --- | --- | --- |
| Each row describes one field from one report, and `record_id` is unique. | A stable unit makes findings traceable. It follows the need for explicit data structure discussed by Afifi et al. (2023). | Required identifiers and duplicates are checked; the intended row meaning is a user responsibility. | A structurally valid table may still mix units or count the same evidence more than once. |
| `report_id` identifies a document; study relationships are managed outside the app. | A study can have multiple reports (Li et al., 2024). No study-linkage model is implemented. | Not independently checked. | Report counts must not be presented as numbers of independent studies. |
| Both reviewers use comparable field definitions and units. | A text comparison is meaningful only if it refers to the same item. Shared instructions and piloting are methodological safeguards. | Not inferred from matching field names; review the team's dictionary and pilot. | Matching “10” can hide different units, time points, or populations. |
| One nonblank `(report_id, field)` key identifies at most one comparable item in each file. | This avoids arbitrary pairing. It is an implementation choice, not a universal extraction format. | Missing or duplicate keys are blocked and reported. | Multi-arm or repeated-time-point records require distinguishable field definitions or external restructuring. |
| Surrounding whitespace can be ignored, while case and internal text remain meaningful. | Trimming reduces incidental differences without interpreting an answer. | Covered by comparison fixtures. | Equivalent scientific answers can still differ; important differences can exist within matching strings. |
| Nonblank agreement and all-pair agreement answer different questions. | Matching blanks should not be hidden inside a percentage about supplied answers. | Separate numerators, denominators, and blank categories are emitted. | Comparing the percentages without their denominators can mislead. |
| A source locator and `Verified` status are statements by the reviewer. | Source reading and scientific adjudication are outside the implemented workflow. | Presence and allowed status labels are checked; source accuracy is untested. | A clean audit can contain unsupported or incorrect answers. |
| A current saved decision is sufficient for this session. | The prototype keeps only the latest decision per pair. It is a practical scope choice. | Replacement and input binding have software tests. | Earlier decisions cannot be reconstructed unless the user retained separate exports. |
| Input hashes and bundle hashes refer to exact bytes. | Byte comparison detects changes independently of filenames (Python Software Foundation, accessed 2026-10-20). | Recomputed digests and malformed-package tests. | Reformatting can change a digest without changing meaning; a matching digest does not prove correct content. |
| Any supplied expected archive digest comes from a separately trusted record. | Otherwise an archive and its expected hash can be replaced together. RFC 8493 distinguishes integrity from protection against active attacks. | Trust in the external reference is not checked. | The optional comparison provides no independent authentication. |
| File and row limits are suitable for a small prototype. | The 5 MiB, 10,000-row, and 50-column limits bound resources, not scientific adequacy. | Boundary tests enforce them. | A valid large extraction needs another workflow; rejection does not imply poor science. |
| The browser and Python hosting environments are appropriate for the data. | Selected browser-file contents stay in memory; a hosted Python instance receives uploads. These are different data paths. | Local code inspection and existing tests; deployment-specific policies are not verified. | Unapproved hosting or shared devices can expose sensitive information. |
| Synthetic fixtures can verify defined behavior. | Known examples isolate software rules. | Existing Python and JavaScript tests. | They cannot estimate reviewer accuracy, usability, time savings, or clinical benefit. Those remain untested. |

References are in [the source list](references.md); [the audit](reference-audit.json) states what was actually inspected. None of these assumptions establishes that an extraction is ready for scientific synthesis.
